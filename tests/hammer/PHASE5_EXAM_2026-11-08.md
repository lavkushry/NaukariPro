## Findings

### F1 — Submission confirmation on error / negated pages

| Field | Value |
|-------|-------|
| **Severity** | **critical** |
| **Module + function** | `naukari_pro/governed_apply/confirmation.py` → `detect_submission_confirmation` |
| **Oath violation** | **Counts blocked as applied** — ledger `record_confirmed_submit` runs on hostile page text that merely *contains* success substrings. |

**Reproduction:**

```python
from naukari_pro.governed_apply.confirmation import detect_submission_confirmation
from naukari_pro.governed_apply.pipeline import GovernedApplyPipeline

assert detect_submission_confirmation(
    page_text="error: application submitted failed"
).confirmed is True  # matched substring "application submitted"

pipe = GovernedApplyPipeline(
    {"email": "x@y.com"}, dry_run=False, auto_submit=True
)
job = {"url": "http://job", "fit_score": 90, "coverage_pct": 80, "company": "C", "title": "T"}
res = pipe.run_job(
    job,
    dom_fields=[],
    page_text="error: application submitted failed",
    page_url="",
    approved=True,
)
assert res.status == "applied" and res.submitted is True
```

**Root cause:** `CONFIRM_TEXT_PATTERNS` uses unanchored alternation (`application (?:has been )?submitted`, `successfully applied`, etc.) with no negation guard, so validation/error DOM text still matches.

### F2 — Job URL SSRF: hex / octal / DNS-rebind host literals pass validation

| Field | Value |
|-------|-------|
| **Severity** | **critical** |
| **Module + function** | `naukari_pro/hammer_safe.py` → `validate_job_url` / `_is_blocked_ssrf_host` |
| **Oath violation** | **Submit wrong data / SSRF** — attacker-supplied “job” URLs reach fetchers that resolve these hosts to loopback or RFC1918 despite the SSRF gate. |

**Reproduction:**

```python
from naukari_pro.hammer_safe import validate_job_url

for url in (
    "http://0x7f000001/",      # hex → 127.0.0.1
    "http://0177.0.0.1/",       # octal → 127.0.0.1
    "http://127.0.0.1.nip.io/", # public DNS → 127.0.0.1
):
    validate_job_url(url)  # returns normalized URL; does NOT raise
```

**Root cause:** Blocklist only recognizes dotted-decimal / `ipaddress` parseable forms. `urlparse().hostname` leaves `0x7f000001` and `0177.0.0.1` unparsed; `nip.io` labels are treated as public DNS names.

### F3 — Resume grounding accepts fabricated metrics with `ms` suffix

| Field | Value |
|-------|-------|
| **Severity** | **critical** |
| **Module + function** | `naukari_pro/resume_gen/claim_validator.py` → `validate_text` / `NUMBER_RE` |
| **Oath violation** | **Submit wrong data** — unsupported latency/cost numbers pass grounding and can ship in tailored resumes. |

**Reproduction:**

```python
from naukari_pro.resume_gen.claim_validator import validate_text, NUMBER_RE

evidence = ["Reduced latency from 400ms to 180ms"]
sentence = "Reduced latency from 400ms to 999ms."
assert NUMBER_RE.findall(sentence) == []  # regex blind to Nms tokens
report = validate_text(sentence, evidence)
assert report.ok is True and report.unsupported_claims == []
```

**Root cause:** `NUMBER_RE` does not match digits immediately followed by unit suffixes (`ms`, `s`, etc.), so the unsourced-number gate never runs for the fabricated `999ms`.

### F4 — Canonical `security.pii` redactor leaks Google API keys

| Field | Value |
|-------|-------|
| **Severity** | **critical** |
| **Module + function** | `naukari_pro/security/pii.py` → `redact_pii`, `secrets_in_text` |
| **Oath violation** | **Leak secrets/PII** — logs and sinks importing `naukari_pro.security` (public package surface) emit live `AIza…` keys. |

**Reproduction:**

```python
from naukari_pro.security.pii import redact_pii, secrets_in_text
from naukari_pro.hammer_safe import redact_secrets

leak = "AIzaSyAbCdEfGhIjKlMnOpQrStUvWxYz123456"
assert "[REDACTED" not in redact_pii(leak)  # unchanged
assert secrets_in_text(leak) == []           # not detected
assert redact_secrets(leak) == "[REDACTED_SECRET]"  # hammer_safe only
```

**Root cause:** `API_KEY_RE` covers `sk-`, `ghp_`, `xai-` but not `AIza…` (present in `hammer_safe._SECRET_PATTERNS`). Callers using `naukari_pro.security.pii` fail open vs hammer helpers.

### F5 — Ledger records `applied` without confirmation evidence

| Field | Value |
|-------|-------|
| **Severity** | **critical** |
| **Module + function** | `naukari_pro/governed_apply/approval.py` → `ApprovalQueue.record_confirmed_submit` |
| **Oath violation** | **Corrupt ledger / count blocked as applied** — SQL `submissions` row with `status='applied'` and empty confirmation fields. |

**Reproduction:**

```python
import tempfile
from pathlib import Path
from naukari_pro.governed_apply.approval import ApprovalQueue

db = Path(tempfile.mkdtemp()) / "ledger.db"
q = ApprovalQueue(db_path=db)
q.record_confirmed_submit(
    job_url="https://attacker-controlled",
    company="",
    title="",
    confirmation_text=None,
    confirmation_url=None,
)
assert q.submission_count() == 1  # status applied, no confirmation proof
```

**Root cause:** Docstring says “only call after visible ATS confirmation” but the function has **no fail-closed validation** of `confirmation_text` / `confirmation_url` / pattern match; any caller (or future MCP path) can inflate applied counts.
